Asymmetric VR / PC · Unity 6.3 LTS · October 2026

Dumpling Kitchen, rebuilt properly

One player is a chef in VR trying to cook dinner in five minutes. Everyone else is a dumpling on a PC, turning off the gas, unplugging the rice cooker, killing the lights and knocking the chef's hat over their eyes. This guide rebuilds it from an empty project, the way a studio would.

  • Unity 6.3 LTS
  • URP
  • OpenXR 1.18
  • XR Interaction Toolkit 3.6
  • Input System 1.20
  • Netcode for GameObjects 2.13
  • Multiplayer Services 2.4 (Relay)

How to use this guide

It's written for you coming back after four years: you know what a GameObject and a prefab are, you've written C#, and you've used Mirror. It explains why as well as what, because the why is what makes the habits stick.

  • Part 1 builds the whole game as a couch game on one PC: the Quest 2 for the chef and split-screen with gamepads/keyboard for the dumplings. No networking yet, so you can focus on clean game code.
  • Part 2 converts it to networked play with Netcode for GameObjects: the chef hosts, dumplings join over LAN or the internet.
  • Every script is complete and copy-pasteable. The same files are in the repo under docs/tutorial/code/ so you can copy whole folders.
  • Tick chapters off in the sidebar as you go. Ticks are saved in this browser only.

The game you're building

VR · 1 player

The chef

  • Cook the dish on the order ticket: put ingredients in a pot, put the pot on a heat source, wait until cooked (not burnt).
  • Serve: put the cooked ingredients on the serving counter.
  • Fix sabotage by grabbing or pressing the broken thing.
  • Wins by serving 3 dishes before the timer runs out.
PC · 1–4 players

The dumplings

  • Run, jump and climb around the kitchen.
  • Walk up to things and press Interact: gas valve, light switch, plugs, pots, the chef's hat.
  • Win if the chef hasn't served 3 dishes when time runs out.
Round · 5 minutes

The flow

  • Dumplings join. The chef rings the service bell.
  • 3, 2, 1 countdown, then a 5:00 round.
  • Results for 10 seconds, then back to waiting.

The details (how many dishes, how long cooking takes, what each sabotage does) are deliberately simple and live in data assets, so you can redesign them without touching the core code.

What you need

  • A Windows 10/11 PC with a VR-capable GPU. PC VR through Link is Windows only.
  • Your Quest 2, plus either a USB 3 cable (Link) or 5 GHz Wi-Fi (Air Link). Steam with SteamVR installed if you want the SteamVR route.
  • One or more gamepads (any XInput or PlayStation pad), or just the keyboard and mouse.
  • About 25 GB of free disk space, Git with Git LFS, and a Unity ID.

Setup · 45 min

Install Unity and create the project

Install the tools

  1. Install Unity Hub from unity.com and sign in with your Unity ID.
  2. In Hub > Installs > Install Editor, choose the latest Unity 6.3 LTS (6000.3.x). Add modules: Windows Build Support (IL2CPP) and Documentation. Android Build Support is only needed if you later want a standalone Quest build.
  3. Install a C# IDE. Any of these is fine:
    • JetBrains Rider (free for non-commercial use) has the best Unity integration. You used it in 2022 (the repo has a .idea folder).
    • Visual Studio 2022 Community with the "Game development with Unity" workload.
    • VS Code with the official Unity extension.
    Then in Unity: Edit > Preferences > External Tools > External Script Editor.
  4. Install Git and run git lfs install once.

Create the project

  1. Hub > New project > Universal 3D template. Name it DumplingKitchen. Untick "Connect to Unity Cloud" for now (we link it in Chapter 17).
  2. When it opens, delete the sample Assets/Scenes/SampleScene and the TutorialInfo folder if present.
  3. Edit > Project Settings > Player > Other Settings: check Active Input Handling is Input System Package (New).
Review D3

I picked the plain Universal 3D template over Unity's VR template. The VR template pre-installs everything in Chapter 4 plus sample content. Adding the pieces yourself is slower but you'll know what each one does, which pays off the first time something breaks.

Turn on fast Play mode

Edit > Project Settings > Editor > Enter Play Mode Settings: set it to Reload Scene only (in older wording: tick "Enter Play Mode Options", untick "Reload Domain"). Pressing Play becomes near instant instead of several seconds.

Gotcha · static fields survive Play

Without a domain reload, static fields and static events keep their values from the previous Play session. Every script in this guide that has statics resets them with this pattern:

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetStatics() => Instance = null;

If you add a static, add it to a reset method too.

Git, folders, assemblies and code style

This is the "boring" chapter that separates a hobby project from one that survives a year and a team. Do it before writing gameplay; it's painful to retrofit.

Version control

  1. In the project folder: git init. Add Unity's standard .gitignore (GitHub's Unity.gitignore template; your 2022 repos already used it).
  2. Add a .gitattributes so big binary files go to Git LFS and scenes merge sensibly:
# Text assets: let git merge them, with Unity's YAML merge tool if configured
*.cs        text diff=csharp
*.unity     text merge=unityyamlmerge eol=lf
*.prefab    text merge=unityyamlmerge eol=lf
*.asset     text merge=unityyamlmerge eol=lf
*.mat       text merge=unityyamlmerge eol=lf
*.meta      text eol=lf

# Binary art and audio: store in Git LFS
*.fbx  filter=lfs diff=lfs merge=lfs -text
*.png  filter=lfs diff=lfs merge=lfs -text
*.psd  filter=lfs diff=lfs merge=lfs -text
*.tga  filter=lfs diff=lfs merge=lfs -text
*.wav  filter=lfs diff=lfs merge=lfs -text
*.mp3  filter=lfs diff=lfs merge=lfs -text
*.ogg  filter=lfs diff=lfs merge=lfs -text
  1. Check Edit > Project Settings > Editor: Version Control Mode = Visible Meta Files, Asset Serialization = Force Text (both are the defaults in Unity 6).
  2. Commit early: git add . && git commit -m "Empty URP project".
Why · LFS and smart merge

Your 2022 repos stored every FBX and PNG straight in git (NewVRDumpling's history is over a gigabyte). LFS keeps the repo fast to clone. unityyamlmerge is Unity's scene-aware merge tool; to switch it on, point git at it once per machine (Unity's manual page "Smart merge" has the two config lines for your install path).

Folder structure

Everything we make goes under Assets/_Project. The underscore sorts it to the top, and it keeps our work separate from packages and Asset Store imports that land in their own folders.

Assets/ └─ _Project/ ├─ Art/ Models, Materials, Textures, Animations (by type) ├─ Audio/ ├─ Input/ Dumpling.inputactions ├─ Prefabs/ Chef/, Dumplings/, Kitchen/, Sabotage/, UI/, Systems/ ├─ Scenes/ Kitchen (Part 1); + Bootstrap, Menu (Part 2) ├─ Settings/ URP assets, GameConfig, Ingredient and Recipe assets ├─ Scripts/ by FEATURE: Core, Game, Cooking, Chef, Dumplings, Sabotage, UI, Local, Net │ └─ DumplingKitchen.Runtime.asmdef ├─ Editor/ editor-only tools (Part 2) └─ Tests/ └─ EditMode/ DumplingKitchen.Tests.EditMode.asmdef
Why · scripts by feature, assets by type

When you work on sabotage you open Scripts/Sabotage and everything is there. Art is the opposite: artists think "all the models", so art is grouped by type. Namespaces mirror script folders (DumplingKitchen.Sabotage), so you can always find a class from its namespace.

Then → now

Big-Project grouped code by person (Prototypes/LaraTutorials, KieranTutorials) and used namespaces like Lara. That's fine for learning spikes, but production code is owned by the team and grouped by what it does.

Assembly definitions

Create the two .asmdef files below (right-click > Create > Scripting > Assembly Definition, then paste the content in your IDE, or copy the files from docs/tutorial/code/part1-local).

Why · assembly definitions
  • Faster iteration: Unity only recompiles assemblies that changed, instead of every script in the project.
  • Enforced dependencies: our code can only use packages listed in references. Accidental dependencies become compile errors instead of surprises.
  • Tests: the test assembly can see the game code, and the game never ships with test code.
Gotcha

Once an asmdef exists, scripts outside its folder (in the default Assembly-CSharp) can see our code, but our code can't see theirs. Keep all your scripts under _Project/Scripts. If a package's types "don't exist" in your code, its assembly is missing from references.

Review D5, D6

Working title Dumpling Kitchen, namespace DumplingKitchen, one runtime assembly. Split into more assemblies when compile times grow.

Why · [SerializeField] private instead of public

A public field lets any script change it at any time, and you lose track of who did. [SerializeField] private shows it in the Inspector but keeps code access closed. Expose read-only properties (public float MoveSpeed => moveSpeed;) when other code needs to read it. This is encapsulation, the first pillar of OOP, applied to Unity.

Then → now

Big-Project's VrWristUI had public GameObject wristUI; and public bool activeWristUI;, both writable from anywhere. The new scripts keep fields private and expose read-only properties, like ChefRigAnchors in Chapter 15.

VR setup · 1 hour

VR: Quest 2 via Link and via SteamVR

OpenXR is a standard API that every headset runtime implements. Your game talks to OpenXR; OpenXR talks to whichever runtime is active on the PC. For your Quest 2 there are two runtimes you care about:

RouteRuntimeHow the Quest connectsGood for
Meta LinkMeta Horizon Link (the PC app, formerly "Oculus app")Link cable or Air Link (Wi-Fi)Lowest latency, fewest moving parts. Use this day to day
SteamVRSteamVRSteam Link app on the Quest (wireless), or Link/Air Link with SteamVR running on topTesting what Steam players will get; Index/Vive controllers if you ever borrow them

The same build works with both. That's the big win over 2022, when the SteamVR plugin and Oculus Integration were separate code paths.

Install the XR packages

  1. Edit > Project Settings > XR Plug-in Management > click Install XR Plugin Management if asked.
  2. On the Windows, Mac, Linux tab, tick OpenXR. Unity installs the OpenXR package.
  3. Keep Initialize XR on Startup ticked for Part 1. (Part 2 turns it off.)
  4. Window > Package Manager > Unity Registry: install XR Interaction Toolkit (3.6.x). In its Samples tab, import Starter Assets and XR Interaction Simulator.
  5. If Unity asks to enable the new Input System backends or restart, say yes.

Configure OpenXR

  1. Project Settings > XR Plug-in Management > OpenXR (Windows tab).
  2. Enabled Interaction Profiles: add Oculus Touch Controller Profile (Quest 2). Also add Meta Quest Touch Plus Controller Profile (Quest 3), Valve Index Controller Profile and HTC Vive Controller Profile so friends' headsets work too.
  3. Render Mode: Single Pass Instanced (renders both eyes in one pass; roughly half the draw-call cost).
  4. Open Project Validation (the section just under OpenXR) and click Fix All.
  5. Player > Other Settings > uncheck Auto Graphics API for Windows and put Direct3D11 at the top.
Gotcha · D3D11, not Vulkan

There are open Unity issues where the editor exits Play mode on the first frame with SteamVR + Vulkan, and crashes with SteamVR + Quest Link in some Unity 6 versions. D3D11 avoids the first. If you hit the second, turn on the Meta compatibility option in SteamVR's developer settings, or use the Meta Link runtime for editor work.

Route A: Meta Horizon Link / Air Link

  1. Install the Meta Horizon Link app on the PC and pair your Quest 2.
  2. In the app: Settings > General > OpenXR Runtime > Set Meta Horizon Link as active.
  3. Cable: plug in a USB 3 cable and accept "Enable Link" in the headset. Wireless: in the headset, Settings > System > Quest Link > turn on Air Link and connect to your PC. Use 5 GHz Wi-Fi, ideally with the PC wired to the router.
  4. You should see the Link home environment in the headset. Leave it running.

Route B: SteamVR

  1. Install Steam and SteamVR.
  2. Connect the Quest: either install the Steam Link app on the Quest and connect wirelessly, or connect with Link/Air Link first and then start SteamVR on the PC.
  3. SteamVR > Settings > OpenXR > Set SteamVR as OpenXR Runtime.

Switch runtimes without changing system settings

In Project Settings > XR Plug-in Management > OpenXR (Windows tab), the Play Mode OpenXR Runtime dropdown overrides the runtime for Play mode only: System Default, Oculus, or SteamVR. It resets to System Default when you restart Unity. Built games always use the system's active runtime (whichever app you last set as active).

Smoke test: grab a cube

  1. Create Assets/_Project/Scenes/Kitchen.unity and open it. Delete the default Main Camera.
  2. From Samples/XR Interaction Toolkit/3.6.x/Starter Assets/Prefabs, drag XR Origin (XR Rig) into the scene. It contains the tracked camera, both controllers with near-far interactors, locomotion, and an Input Action Manager that switches the XR input actions on.
  3. Add GameObject > XR > Interaction Manager (XRI would create one on demand, but an explicit one is easier to find) and GameObject > XR > UI Event System so world-space canvases respond to controller rays.
  4. Add a floor (Plane) and a Cube at waist height. On the cube add a Rigidbody and an XR Grab Interactable.
  5. Put the headset on, press Play, reach out and grab the cube with the grip button.
  6. No headset handy? Drag XR Interaction Simulator (from the simulator sample) into the scene and drive the rig with mouse and keyboard. Remove it before playing with the headset.
Why · test the plumbing first

When something doesn't work in VR it's either your code or the runtime/headset/driver stack. Proving the stack works with one cube, before writing any game code, halves the places to look later.

Plain OpenXR, no Meta XR SDK. Everything in this game works on PC VR with OpenXR alone. Add Meta's packages later if you want passthrough, Meta-specific hand-tracking features, or a standalone Quest build.

Bring the old art home

NewVRDumpling has the most complete set of the team's models: 44 kitchen FBX files plus the dumpling. Big-Project's 32 models are a subset.

  1. Clone NewVRDumpling somewhere outside your new project.
  2. Copy these into Assets/_Project/Art/Models/, without their .meta files: everything in Assets/Kitchen Models/, and Assets/Model/Dumpling.fbx.
  3. Select all the models. In the Inspector's Model tab check the scale against something you know: the Env_Kitchen_1.5x2m module should measure 1.5 × 2 m (a default Cube is 1 m). Fix with Scale Factor if needed.
  4. Materials tab > Extract Materials... into Art/Materials. Select the extracted materials and set their shader to Universal Render Pipeline/Lit (or run Window > Rendering > Render Pipeline Converter).

Why · copy without the .meta files

A .meta file holds the asset's GUID and import settings. The old ones point at Built-in materials and old import defaults. Letting Unity 6 generate fresh ones gives you clean URP imports. The cost: the old Kitchen_Populated.prefab won't link up, so treat it as a layout reference and rebuild the layout in the new project.

Prefabs and prefab variants

A good habit: keep the imported model untouched, and build gameplay prefabs on top of it.

Prop_Wok.fbx imported model (never edit) └─ Prop_Wok.prefab model + Rigidbody + Collider + XR Grab Interactable + CookingVessel └─ Prop_Wok_Net.prefab prefab VARIANT, Part 2: + NetworkObject + NetworkTransform + NetworkRigidbody

A prefab variant inherits everything from its base and stores only the differences. Change the base wok's collider and the networked variant gets it too. It's inheritance, for assets.

Some targets work best as an invisible trigger collider (a big "reach zone" around the chef's hat, say). Concepts · 20 min read

Architecture: how the pieces talk

Before any gameplay code, here's the shape of the whole thing. Every script in this guide follows the same few rules, and knowing them up front makes each chapter read as "another example of the rule" instead of a new idea.

Five tools, five jobs

ToolUse it forIn this game
Components (composition)Building objects out of small single-purpose behavioursA dumpling = DumplingMotor + DumplingCamera + DumplingInteractor + ...
InheritanceA family of things that share rules and differ in detailsSabotageTarget → GasValve, LightSwitch, PowerPlug...
InterfacesA capability that unrelated classes can shareIHeatSource (stove and electric hob), IDumplingInteractable, IDumplingInput
ScriptableObjectsShared data and tuning, edited as assetsGameConfig, IngredientDefinition, RecipeDefinition
Plain C# classesRules and logic that don't need a GameObjectRoundTimer, CookingLogic, TriggerTracker<T>
Why · "composition over inheritance", but not "never inheritance"

Unity is built on composition: a GameObject is a bag of components. Use deep inheritance for GameObjects and you end up with FlyingSwimmingDumpling : SwimmingDumpling : Dumpling. But for a genuine family with shared rules, like every sabotage target, a base class is the right tool: the rules live in one place and each subclass is ten lines.

Which code may know about which

Each folder is a module. Arrows mean "uses". They all point towards the stable core and never back, so you can change the UI without touching game rules, and add sabotages without touching dumplings.

Call down, signal up

  • When a system needs something done, it calls a method on the thing that owns it: the serving counter calls RoundManager.ReportDishServed().
  • When a system has news, it raises a C# event and doesn't care who listens: RoundManager.PhaseChanged, SabotageTarget.AnySabotaged.
  • UI only ever listens and reads. It never changes game state.
Gotcha · every += needs a -=

Subscribe in OnEnable (or Start) and unsubscribe in OnDisable (or OnDestroy). An event holding a reference to a destroyed object throws MissingReferenceException the next time it fires, usually after a scene reload, far from the real bug.

The Unity lifecycle, and what goes where

MessageWhenUse it to

Where every script lives

The full index with one line per script is in Appendix A. In short:

Scripts/ ├─ Core/ GameConfig, RoundTimer, TriggerTracker, CameraUtility (no game knowledge) ├─ Game/ GamePhase, RoundManager (the rules of a round) ├─ Cooking/ IHeatSource, Stove, ElectricAppliance, ElectricHob, HeatZone, CookingVessel, │ Ingredient, IngredientDefinition, CookingLogic, RecipeDefinition, ServingCounter ├─ Chef/ ChefRestoreHandle, ChefVisionBlocker (+ ChefRigAnchors in Part 2) ├─ Dumplings/ IDumplingInput, PlayerDumplingInput, DumplingMotor, DumplingCamera, │ IDumplingInteractable, DumplingInteractor, DumplingPlayer ├─ Sabotage/ SabotageTarget, GasValve, LightSwitch, PowerPlug, Knockable, ChefHat ├─ UI/ RoundDisplay, OrderTicketDisplay, SabotageAlertDisplay, InteractionPromptDisplay ├─ Local/ LocalPlayerJoiner, DesktopViewSetup (Part 1 only) └─ Net/ Part 2

SOLID, in kitchen terms

  • Single responsibility: ChefHat moves the hat; ChefVisionBlocker blinds the chef. Two jobs, two classes.
  • Open/closed: add a new sabotage by adding a class. Nothing existing changes.
  • Liskov substitution: the interactor works with any IDumplingInteractable, and any SabotageTarget subclass behaves correctly when treated as the base type.
  • Interface segregation: IHeatSource has two members. Pots don't need to know a stove has a flame particle.
  • Dependency inversion: the motor depends on IDumplingInput, not on the keyboard. That's what lets Part 2 swap in network-driven dumplings without touching the motor.
Review D15

The round is reachable through a small singleton (RoundManager.Instance) and a couple of static events. It's the most readable option for a returning developer. Bigger teams often use ScriptableObject event channels or a dependency-injection container (VContainer, Zenject) instead; the rest of the design doesn't change if you switch.

Core gameplay · 1.5 hours

The round: config, timer, state machine

The heart of any round-based game is a state machine: the game is always in exactly one phase, and moves between phases on clear triggers.

Step 1 · GameConfig: numbers belong in data

Create the asset: right-click _Project/Settings > Create > Dumpling Kitchen > Game Config. Leave the defaults (300 s round) for now.

Why · ScriptableObject config

No magic numbers in code. You can keep several configs ("GameConfig_Quick" with 60 s rounds for testing) and swap them in the Inspector. Properties are read-only, so nothing can change the rules at runtime by accident.

Review D7, D8, D9

300 s rounds, 3 s countdown, 10 s results, the chef needs 3 dishes and wins the moment they serve the third, minimum 1 dumpling to start. All tweakable in this asset.

Step 2 · RoundTimer: a plain C# class, with tests

Because RoundTimer isn't a MonoBehaviour, we can test it in milliseconds without a scene:

Run them: Window > General > Test Runner > EditMode > Run All. All green? Good. Break Format on purpose and watch a test fail, so you trust them.

Why · pull logic out of MonoBehaviours

Testing a MonoBehaviour means building a scene and waiting for frames. Testing a plain class means calling methods. The pattern you'll see repeatedly: keep MonoBehaviours thin (Unity glue), and put rules in plain classes or pure functions that are easy to test.

Step 3 · RoundManager: the state machine

Things to notice:

  • Every phase change goes through one method, EnterPhase, which also fires PhaseChanged. There is no other way to change phase, so listeners can never miss one.
  • Report... methods check the phase themselves. A dish served during the countdown simply doesn't count. Callers don't need to know the rules.
  • The score fields have private set. Only the round can change the score.
Why · an enum + switch is enough (for now)

With four phases that only differ in "what happens when the timer ends", an enum and a switch is the clearest code. When phases start having lots of their own behaviour (music, camera moves, different rules), refactor to the State pattern: one class per phase with Enter(), Tick(), Exit().

Then → now

Big-Project's CustomNetworkManager did connection handling, lobby rules, readiness, scene changes and player spawning in one class. Here the round rules live in RoundManager and connection handling (Part 2) lives in ConnectionManager. Smaller classes with one reason to change are much easier to come back to after a break.

Step 5 · Scene setup

Lay out the Kitchen scene's hierarchy with empty "header" objects. Keep them at position 0,0,0 with no components so they're purely organisational:

  1. Create the RoundManager object and assign your GameConfig.
  2. Create both canvases, each with TextMeshPro texts for timer, phase and score, and a RoundDisplay wired to them. Put the wall clock somewhere the chef can see it above the stove.
  3. The service bell: a small cylinder with a collider and an XR Simple Interactable. In the interactable's Interactable Events, add a Select Entered entry, drag in the RoundManager object and pick RoundManager.StartRound.

Why · a UnityEvent for the bell, C# events in code

The chef: cooking

The cooking loop: ingredient → pot → heat → cooked → serving counter → dish served. Each arrow is a different class, and each class only knows its neighbour.

Step 1 · Heat sources: an interface and a base class

Why · interface AND base class here?

They answer different questions. ElectricAppliance answers "can it be unplugged?" and shares the power-handling code. IHeatSource answers "can it cook?" A gas stove can cook but can't be unplugged; a radio can be unplugged but can't cook; an electric hob is both. C# only allows one base class but any number of interfaces, which is exactly why capabilities are usually interfaces.

  1. Create three materials per ingredient (raw, cooked, burnt) by duplicating the extracted material and tinting it. A quick shortcut: one shared "Burnt" material for everything.

Core gameplay · 2.5 hours

Sabotage: the OOP showcase

This chapter is where the design pays off. Five different sabotages, one set of rules, and adding a sixth takes about ten lines.

Step 1 · What a dumpling can interact with

Why · NonAlloc physics queries

Physics.OverlapSphere returns a new array every call. Called every frame by four dumplings, that's a steady stream of garbage, and garbage collection pauses are dropped frames, which in VR the chef can feel. OverlapSphereNonAlloc writes into an array we allocated once.

Gotcha · interfaces and destroyed objects

Unity's "fake null" (a destroyed object that == null) only works on variables typed as a Unity object. A destroyed component held in an interface variable is not null. DumplingInteractor.IsAlive handles it; remember the trick for your own interface references.

Step 2 · The base class: rules in one place

Why · the Template Method pattern

Interact() is the template: check the rules, run the hooks, update the score. It's not virtual, so no subclass can forget the cooldown or skip telling the round manager. Subclasses fill in the hooks:

  • OnSabotagedBy(dumpling): one-off effect from a specific dumpling (a shove). Optional.
  • OnSabotaged() / OnRestored(): make the world match the state. Required.

Keep this split in mind: one-off effects vs state. It's exactly the split networking needs in Part 2, and it's why the subclasses won't change there.

Concepts · 25 min read

Networking concepts

You used Mirror in 2022, so most of this will feel familiar. Netcode for GameObjects (NGO) uses the same model; the names are different.

IdeaMirror (2022)NGO 2.x
Networked objectNetworkIdentityNetworkObject
Networked scriptNetworkBehaviourNetworkBehaviour
Replicated state[SyncVar(hook = ...)]NetworkVariable<T> + OnValueChanged
Client → server call[Command] CmdX()[Rpc(SendTo.Server)] XRpc()
Server → clients call[ClientRpc] RpcX()[Rpc(SendTo.Everyone)] (or NotServer, Owner...)
"Is this mine?"hasAuthority / isLocalPlayerIsOwner / IsLocalPlayer

Spawning a playerNetworkServer.AddPlayerForConnectionNetworkObject.SpawnAsPlayerObject(clientId)

Four rules for this game

  1. The server decides. Whether a sabotage happened, whether food is cooked, what time it is: one machine owns each truth, and everyone else is told.
  2. State goes in NetworkVariables, events go in RPCs. "The gas is off" is state: someone joining late must see it. "Play the ding sound" is an event: it only matters now.
  3. Never trust the client. A request from a dumpling is a request. The server re-checks everything (is the round on, are you close enough, is it already broken?) before acting.
  4. Send the least you can. Send "the round ends at server time 812.4" once, not "4:59, 4:58..." every frame. Send "cooked", not the heat value.

Who hosts? The chef.

A host is a server that's also a player. We make the chef's PC the host, every time.

  • The chef grabs pots, stirs, throws things. On the host, all that physics is local, so it feels instant in VR. Lag in VR is nauseating; lag for a dumpling just feels a bit floaty.
  • Kitchen props are owned by the server, which is the chef, so grabbing them never needs an ownership hand-over.
  • Dumplings move their own bodies (owner authority) for responsive controls, and send requests to sabotage things.
Review D21, D22, D23

Chef always hosts; dumpling movement is owner-authoritative; every request is validated on the server. The cost: if the chef quits, the game ends (no host migration). That's normal for this kind of game.

Networking the game rules

Here's where the Part 1 architecture pays back. Only five gameplay files change, and the UI, the dumpling code and all five sabotage subclasses stay exactly as they were.

RoundManager

Why · same public API

Compare it with Part 1: Phase, SecondsRemaining, PhaseChanged, ScoreChanged, StartRound() and the Report... methods have the same names and meanings. RoundDisplay doesn't know or care that the numbers now come over the network. Designing the public surface first, then changing what's behind it, is how you keep big changes small.

Gotcha · NetworkBehaviour already has OnDestroy

NetworkBehaviour defines public virtual void OnDestroy(). Override it and call base.OnDestroy(), or NGO's own clean-up won't run.

SabotageTarget (and why the subclasses don't change)

In Part 1 we split each sabotage into a one-off effect (OnSabotagedBy) and state presentation (OnSabotaged/OnRestored). The networked base runs the one-off effect on the server only, and runs the state presentation on every machine when the NetworkVariable changes. GasValve, LightSwitch, PowerPlug, Knockable and ChefHat compile and work unchanged. Each sabotage target in the scene needs a NetworkObject on it or a parent.

Gotcha · one NetworkObject per thing

Don't nest a NetworkObject inside another one in a prefab. A pot is one NetworkObject; its child trigger is just a child. If the chef needs to carry a NetworkObject that sits inside another (food in a pot), that's fine at runtime because they're separate objects moving with physics.

How this code was checked

Every script was compiled with a real C# 9 compiler against stubs of the Unity APIs it uses, and the API names were checked against the actual package sources (NGO 2.13.3, XRI 3.6.1, Input System 1.20.1, Multiplayer Services 2.4.0).
