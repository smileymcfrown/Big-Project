Networking concepts

You used Mirror in 2022, so most of this will feel familiar. Netcode for GameObjects (NGO) uses the same model; the names are different.

IdeaMirror (2022)NGO 2.x

Client → server call[Command] CmdX()[Rpc(SendTo.Server)] XRpc()

Four rules for this game

  1. The server decides. Whether a sabotage happened, whether food is cooked, what time it is: one machine owns each truth, and everyone else is told.
  2. State goes in NetworkVariables, events go in RPCs. "The gas is off" is state: someone joining late must see it. "Play the ding sound" is an event: it only matters now.
  3. Never trust the client. A request from a dumpling is a request. The server re-checks everything (is the round on, are you close enough, is it already broken?) before acting.
  4. Send the least you can. Send "the round ends at server time 812.4" once, not "4:59, 4:58..." every frame. Send "cooked", not the heat value.

Who hosts? The chef.

A host is a server that's also a player. We make the chef's PC the host, every time.

  • The chef grabs pots, stirs, throws things. On the host, all that physics is local, so it feels instant in VR. Lag in VR is nauseating; lag for a dumpling just feels a bit floaty.
  • Kitchen props are owned by the server, which is the chef, so grabbing them never needs an ownership hand-over.
  • Dumplings move their own bodies (owner authority) for responsive controls, and send requests to sabotage things.
Review D21, D22, D23

Chef always hosts; dumpling movement is owner-authoritative; every request is validated on the server. The cost: if the chef quits, the game ends (no host migration). That's normal for this kind of game.

The dumplings

  1. Right-click the Dumpling prefab > Create > Prefab Variant, name it Dumpling_Net.
  2. On the variant add NetworkObject, NetworkTransform (Authority Mode: Owner), NetworkRigidbody and NetworkDumpling.
  3. Disable (untick) in the variant: PlayerInput, PlayerDumplingInput, DumplingMotor, DumplingInteractor; and deactivate the CameraRig and PromptCanvas children. List them in NetworkDumpling's owner-only fields.
  4. Add an AudioListener to the variant's camera. In Part 2 each dumpling PC needs its own, and it's only active for the owner.
  5. Add Dumpling_Net to the Network Prefabs List.
Why · disabled by default, enabled for the owner

Every PC creates a copy of every dumpling. If PlayerInput were enabled in the prefab, each copy would grab the local keyboard the moment it spawned, for one frame, before being switched off. Starting disabled and turning on only what the owner needs avoids a whole class of "why did my input go to the wrong dumpling" bugs.

The spawner

  1. In Kitchen, add --- Systems --- / KitchenSpawner with a NetworkObject and KitchenSpawner. Assign both prefabs and the spawn points.
  2. Delete the Part 1 DumplingJoiner object (Player Input Manager, LocalPlayerJoiner, DesktopViewSetup). Keep the lobby camera for dumpling PCs to look through before their dumpling spawns.
Gotcha · spawn after the client has loaded

A client that connects has to load the Kitchen scene before its dumpling can appear. OnSynchronizeComplete fires on the server exactly when that's done, which is why the spawner listens to it instead of OnClientConnectedCallback.

Networking · 2 hours

Networking the game rules

Here's where the Part 1 architecture pays back. Only five gameplay files change, and the UI, the dumpling code and all five sabotage subclasses stay exactly as they were.

FileChange
RoundManagerState → NetworkVariables; timer → one "phase ends at" server time
SabotageTargetState → NetworkVariable; Interact → server RPC with validation
IngredientCook state → NetworkVariable; heat counted on the server only
ServingCounterMenu index → NetworkVariable; serving is server-only; Despawn instead of Destroy
HeatZoneOne line: only the authority cooks
Everything elseUnchanged

RoundManager

Why · same public API

Compare it with Part 1: Phase, SecondsRemaining, PhaseChanged, ScoreChanged, StartRound() and the Report... methods have the same names and meanings. RoundDisplay doesn't know or care that the numbers now come over the network. Designing the public surface first, then changing what's behind it, is how you keep big changes small.

Gotcha · NetworkBehaviour already has OnDestroy

NetworkBehaviour defines public virtual void OnDestroy(). Override it and call base.OnDestroy(), or NGO's own clean-up won't run.

SabotageTarget (and why the subclasses don't change)

In Part 1 we split each sabotage into a one-off effect (OnSabotagedBy) and state presentation (OnSabotaged/OnRestored). The networked base runs the one-off effect on the server only, and runs the state presentation on every machine when the NetworkVariable changes. GasValve, LightSwitch, PowerPlug, Knockable and ChefHat compile and work unchanged. Each sabotage target in the scene needs a NetworkObject on it or a parent.

Cooking

  1. Make _Net prefab variants of every ingredient and grabbable prop: + NetworkObject, NetworkTransform (Server), NetworkRigidbody. Add them to the Network Prefabs List.
  2. Swap the scene's props for the _Net variants. In-scene NetworkObjects are spawned automatically when the host loads the scene.
  3. Give ServingCounter and RoundManager a NetworkObject each.
Gotcha · one NetworkObject per thing

Don't nest a NetworkObject inside another one in a prefab. A pot is one NetworkObject; its child trigger is just a child. If the chef needs to carry a NetworkObject that sits inside another (food in a pot), that's fine at runtime because they're separate objects moving with physics.

Testing · 1.5 hours

Test locally, then play online

Multiplayer Play Mode: four players in one editor

  1. Window > Multiplayer > Multiplayer Play Mode. Activate Player 2 and Player 3. Each becomes a separate virtual editor window running the same project.
  2. Press Play. In the main editor (where the headset is), click Host as Chef. VR starts and the Kitchen loads.
  3. In each virtual player, leave the IP as 127.0.0.1 and click Join as Dumpling. A dumpling appears for each; the chef sees them in the headset.
  4. Run the Chapter 11 checklist again, but across windows.
Why · test with fake lag

On one machine everything is instant, which hides bugs. Add a Network Simulator component (from Multiplayer Tools) to the NetworkManager and pick a preset with around 100 ms delay and a little packet loss. If the game still feels right, it'll feel right over the internet. (Unity Transport's old Debug Simulator fields are obsolete and do nothing in NGO 2.13.)

Two PCs on the same network

  1. File > Build Profiles > Windows > Build. The same build works for chef and dumplings.
  2. On the chef's PC: run it, Host as Chef. Allow it through Windows Firewall when asked (Private networks).
  3. Find the chef PC's IPv4 address (ipconfig). On the other PC: type it, Join as Dumpling.

Online with Relay

  1. Edit > Project Settings > Services: link the project to a Unity Cloud project (create one if needed).
  2. In the Unity Cloud dashboard, enable Relay for the project (there's a free tier).
  3. Chef: Host Online. The join code appears on the kitchen's order board.
  4. Dumplings: type the code, Join Online. No port forwarding needed.
Gotcha · services sign-in in virtual players

Anonymous sign-in stores a player ID per install. Multiplayer Play Mode's virtual players handle this for you; if two built copies on the same PC fight over one identity, test Relay from separate PCs or user accounts.

Next steps

Where next

You have a complete, cleanly structured asymmetric VR/PC game. Here's where to take it, roughly in order of fun per hour.

Game design knobs (no new code)

  • GameConfig: round length, dishes to win, player counts.
  • IngredientDefinition: cook and burn times per ingredient.
  • RecipeDefinition: what each dish needs, how many dishes are on the menu.
  • Each sabotage target's re-arm time, and the dumpling's reach.

Small features that teach a lot

  • Haptics when something is sabotaged: XRI interactors can send haptic impulses to the chef's controllers.
  • The chef grabs and throws dumplings (Kieran's throw experiment): an XR Grab Interactable on the dumpling. In Part 2 the dumpling is client-owned, so ask the server to take temporary ownership first. A good ownership exercise.
  • Chopping: revive Cut.cs as a ChoppingBoard that turns a whole cucumber into slices.
  • Dumpling selection (Lara's DumplingSelection): a NetworkVariable on NetworkDumpling for the chosen model.
  • Sound and juice: an audio manager listening to the static sabotage events.

Engineering habits to add next

  • Profile in VR early: Window > Analysis > Profiler while playing in the headset. Aim for a steady 72/90 fps on the Quest 2 refresh rate you use.
  • Object pooling for anything spawned often (ingredients from a crate dispenser).
  • PlayMode tests for interactions (spawn a pot, a stove, wait, assert cooked).
  • Continuous integration: GameCI on GitHub Actions can run your tests and make builds on every push.

Bigger steps

  • Mixed mode: let a hosted game also accept couch dumplings on the chef's PC, as server-owned dumplings driven by local PlayerInputs. IDumplingInput already makes this possible; the work is in NetworkDumpling's "who controls this?" check.
  • Standalone Quest build (Android): add the Meta OpenXR feature group, then the chef can host from the headset with no PC.
  • Unity 6.7 LTS + NGO 3 when it ships.
