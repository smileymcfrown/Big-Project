Chef gameplay · 2 hours

The chef: cooking

The cooking loop: ingredient → pot → heat → cooked → serving counter → dish served. Each arrow is a different class, and each class only knows its neighbour.

Step 1 · Heat sources: an interface and a base class

Why · interface AND base class here?

They answer different questions. ElectricAppliance answers "can it be unplugged?" and shares the power-handling code. IHeatSource answers "can it cook?" A gas stove can cook but can't be unplugged; a radio can be unplugged but can't cook; an electric hob is both. C# only allows one base class but any number of interfaces, which is exactly why capabilities are usually interfaces.

Step 3 · Ingredients: data vs state

  1. Create three materials per ingredient (raw, cooked, burnt) by duplicating the extracted material and tinting it. A quick shortcut: one shared "Burnt" material for everything.
  2. Create Ingredient assets in Settings/Ingredients: Carrot (8 s to cook, 10 s to burn), Onion, Egg, Cucumber...
  3. Make an ingredient prefab per model: model + Rigidbody (Collision Detection: Continuous Dynamic) + convex Mesh Collider or a primitive collider + XR Grab Interactable + Ingredient.
Why · sharedMaterial

Reading or writing renderer.material silently clones the material for that one object, and those copies are never cleaned up. Swapping between a few shared materials with sharedMaterial creates nothing and keeps the SRP Batcher happy.

Step 4 · Pots and heat zones (and a reusable helper)

Both the pot ("which ingredients are inside me?") and the stove ("which pots are on me?") need to track what's inside a trigger. That's one helper class, written once:

Stove Stove (+ flame ParticleSystem, burner AudioSource) └─ HeatZone BoxCollider (Is Trigger) a few cm above the burner + HeatZone Prop_Wok Rigidbody, convex colliders, XR Grab Interactable, CookingVessel └─ Contents BoxCollider (Is Trigger) filling the inside of the wok
Gotcha · trigger messages go to the Rigidbody

The Contents trigger is a child, but CookingVessel sits on the wok's root next to the Rigidbody. That works because Unity sends OnTriggerEnter to scripts on the Rigidbody's GameObject for all its child colliders. It also means the vessel hears about its own solid colliders touching the heat zone; TriggerTracker ignores anything that isn't an Ingredient, so that's harmless.

Gotcha · food falling out of a carried pot

On the pot's XR Grab Interactable set Movement Type to Velocity Tracking, so it moves with physics instead of teleporting each frame (teleporting pots leave their contents behind). Ingredients need Continuous Dynamic collision detection.

Step 5 · Recipes and the serving counter

  1. Create two or three Recipe assets ("Stir-fried Veg": carrot + onion; "Egg Fried Rice": egg + onion).
  2. Make a ServingCounter: a counter-top mesh with a BoxCollider (Is Trigger) covering its top, plus ServingCounter with the menu filled in.
  3. Hang an order ticket (world-space canvas + OrderTicketDisplay) above the counter.
  4. Playtest: ring the bell (Min Dumplings 0 for now), put a carrot and onion in the wok, put it on the stove, wait, tip them onto the counter. The dish counter on the wall clock should go up.
Review D12, D13

No plates, fixed menu order, heat-seconds cooking. Easy to extend: a Plate that's itself a TriggerTracker<Ingredient>, random orders, chopping (Lara's Cut.cs cucumber experiment is a good starting point).

Step 2 · Input behind an interface

Then → now
2022 · DumplingMovementCtrl + PlayerCamCtrl

Each script did new Controls(), so movement and camera had separate copies of the actions. Lambdas were subscribed in OnStartAuthority and never unsubscribed. Input reading, Mirror authority and movement were all in one class.

Now · PlayerInput + IDumplingInput

One PlayerInput per player owns that player's actions and devices. One adapter class turns it into IDumplingInput. The motor and camera read the interface, so a network- or AI-driven dumpling is just another implementation.

Step 3 · Movement

Why · buffer input, act in FixedUpdate

Input arrives per frame; physics runs at a fixed rate. If you set velocity in Update the movement speed depends on frame rate, and a jump pressed between two physics steps can be lost. So the event just sets _jumpRequested, and FixedUpdate consumes it.

Review D16

Dumplings are Rigidbodies so they can be shoved, knocked over and (one day) grabbed and thrown by the chef, like Kieran's ThrowObject experiment. If you want tight platforming instead, a CharacterController is simpler.

Step 4 · The camera

Review D17

A small custom orbit camera instead of Cinemachine. In split-screen, Cinemachine 3 needs a separate output channel per player, which is a lot of new concepts on day one. Swapping later only touches this class.

Step 6 · Assemble the Dumpling prefab

Dumpling layer Dumpling · Rigidbody (Interpolate, Continuous Dynamic) · SphereCollider │ PlayerInput · PlayerDumplingInput · DumplingMotor · DumplingInteractor · DumplingPlayer ├─ Body Dumpling.fbx mesh (pivot at the feet) ├─ ReachPoint empty, in front of the dumpling at waist height (DumplingInteractor's reach origin) ├─ CameraRig DumplingCamera (target = Dumpling) │ └─ Camera Camera (Culling Mask: everything except ChefOnly) · NO AudioListener └─ PromptCanvas Canvas (Screen Space - Camera, Camera = the camera above) · InteractionPromptDisplay (Chapter 10)
  1. PlayerInput: Actions = Dumpling, Default Map = Dumpling, Behavior = Invoke C Sharp Events, Camera = the child Camera (needed for split-screen).
  2. DumplingMotor: Ground Layers = everything except Dumpling; View Transform = CameraRig.
  3. Create a Physics Material (Unity 6 calls it PhysicsMaterial) with 0 friction and Friction Combine = Minimum, and put it on the SphereCollider so dumplings don't stick to walls.
  4. Drag one Dumpling into the scene and press Play. WASD/mouse or a gamepad should move it around. Delete it from the scene afterwards; Chapter 11 spawns them.
Gotcha · one AudioListener

Unity wants exactly one AudioListener. In Part 1 it's on the chef's XR camera. Remove it from the dumpling camera or the console fills with warnings when the second dumpling joins.

Then → now

The Week 1 prototype already had a Player Low Friction.physicMaterial. Same idea; the type is now called PhysicsMaterial, and Rigidbody.velocity is now linearVelocity.
